# Drag-move hardening

## Goal

A drag (or the drawer's Ready button) fails typed and visibly or succeeds — no dead interactions. The live paths that break this today: the gating branch of `moveStory` (`src/app/lib/board-store.ts:130-135`) fires `api.story.move` with no optimistic write and discards the `{gating}` result, so a drag into Ready reads as a drag that did nothing (the defect the first live test hit); the RPC-reject rollback (`:140-146`) skips when `lastBoard` is null, a latent trap that would strand the optimistic status; `boardSnapshot()`/`managedRepo()` (`src/server/services/board.ts:20-28`) throw bare `Error`s that surface as untyped 500 toasts when an RPC reaches a stopped service (shutdown — boot order forbids a start race); and the missing-story path (`board-store.ts:110-111`, plus `board-grid.tsx:36-37`'s silent bail above it) no-ops silently in the defensive case of a story removed from the store mid-interaction (its file deleted or re-keyed on disk between snapshots).

## Approach

Measured at `3bbd300`:

- `../stack/plugins/node/src/server/create-node-server.ts:163-175`: `start()` awaits `startServices()` before `serve()` binds the port, so no RPC can race service *start*. The only null window with the server reachable is the board service's own `stop()` (`src/server/services/board.ts:80-84`) — shutdown. Change 4 is defensive typing for that window.
- `src/app/components/board-grid.tsx:31-39` `handleDragEnd`: bails silently when `props.stories[storyId]` is missing. Before the first snapshot nothing renders (grid cards from `props.stories`, drawer's Ready button inside `<Show when={props.story} keyed>`, `card-drawer.tsx:198,217`), so the reachable state is a story removed from the store mid-interaction (file deleted/re-keyed between snapshots). Defensive hardening, verified by reading. The repo compiles under `noUncheckedIndexedAccess` (e.g. `story-card.tsx:28`), so the guard cannot simply be deleted.
- `src/app/lib/board-store.ts:109-147` `moveStory`: `:110-111` returns silently on a missing story; `:130-135` (gating branch, `to === "ready"` only) fires `api.story.move` with only a `.catch`; `:138-146` (optimistic branch, *every* legal transition, `story.move` returning `{gating: false}` for all of them at `routes/story.ts:93`) ignores the resolved result and rolls back only on reject. Stories enter the store only via `applySnapshot` (`:64-87`), which also sets `lastBoard`, and `lastBoard` is never reset to null — so inside `moveStory` (which returns early unless the story is in the store) `lastBoard` is provably non-null, and any null-`lastBoard` fallback would be dead code. The rollback therefore uses a direct revert and never touches `lastBoard`.
- The optimistic branch is reachable with `to === "ready"`: `canTransition` (`src/board/transitions.ts:75-84`) passes on the *client snapshot's* verdict while `requestReady` re-reads fresh (`gate.ts:141-148`) and can find it invalid. The RPC then *resolves* `{gating: true}` — no reject, no rollback — and the overlay (`:66-78`) re-applies the pending `ready` on every later snapshot: a permanently stranded card unless the resolved result is handled.
- `src/server/services/gate.ts:138-180` `requestReady`: `{gating: false}` means `ready` was written. `{gating: true}` covers a fresh round enqueued (`:168-178`), an exhausted attempt re-queued (`:162-166`), and an existing attempt returned untouched in any other phase. Phase `review` is reachable only through `routeFlags` on non-empty `round.flags` (`:230-235`); flags arrive solely via the adversary's `flag_risk` MCP round trip (`kinds.ts:224`, `mcp/tools.ts:229`, `gate.ts:346`), which the stub `claude` never performs — a stub round always auto-passes (`writePass`, `:312-334`).
- The client already owns phase copy: `gate-panel.tsx:14-20` `PHASE_LINES`, a `Record<GatePhase, string>` covering all five phases (`review`: "Contested flags await your call"), and `gate-store.ts:38` `gateFor(storyId)` streams live attempt phases. `gateFor` cannot drive the toast: the gate snapshot rides WS while the move result rides RPC, and nothing orders the two, so the attempt may not have landed when the toast must fire. The RPC result carries the phase; the copy is reused, not duplicated.
- api.md §Errors: every failure is an `ApiError` with an `UPPER_SNAKE` code; message shown verbatim; new failure mode → new registry code. The `story.move` row (api.md:12) must track the return union.
- The stack toast exposes `info` (`../stack/plugins/solid-ui/docs/toast.md:30`); claude-integration.md §Verifying without burning the pool sanctions the stub-`claude` path for the live checks.

Changes:

1. **Missing-story drag fails visibly, owned by `moveStory`** (defensive hardening): `board-grid.tsx:36-37`'s bail becomes `if (props.stories[storyId]?.frontmatter.status === targetStatus) return;`; `board-store.ts:110-111` replaces the silent `return` with `toast.error` naming the story as no longer on the board. Verified by reading: no deterministic live repro.
2. **Rollback simplification** (`board-store.ts:140-146`): capture `from` before the optimistic write; on RPC reject, delete the pending move and revert the story's status directly to `from` (`setStore`). Unconditional, no `lastBoard` dependence, no dead branch — other pending moves are already applied in the store and need no re-overlay.
3. **Phase-aware gating result, precisely scoped**: the wire type is `{ gating: false } | { gating: true; phase: Exclude<GatePhase, "exhausted"> }` (`GatePhase` from `src/shared/gate.ts`). `requestReady` produces the narrow type without a cast: the fresh-attempt and exhausted-retry paths return the literal `"queued"`, and the existing-attempt path returns `existing.phase` after the early-return `=== "exhausted"` check has narrowed it (the `enqueueRound` mutation sits inside the taken branch, so control-flow narrowing holds). `story.move` passes the union through. Client: `PHASE_LINES` moves from `gate-panel.tsx` to `src/app/lib/gate-store.ts` and is imported by both the panel and `board-store.ts` — one copy source, no second map; the toast is `toast.info` composing the story id with `PHASE_LINES[phase]` (so `review` reads "Contested flags await your call"). Branch scoping: the shared piece handles only `{gating: true}` — fire the phase toast, and on the *optimistic* branch additionally drop the pending move and revert to `from` (the server's fresh read invalidated the snapshot's verdict). `{gating: false}` is branch-specific: on the *gating* branch it records the pending move and applies the optimistic `ready` write; on the *optimistic* branch it is a **no-op** — the pending move and status were already written at `:138-139`, and re-stamping `ready` there would corrupt every non-ready legal drag. Keep the existing `.catch` toasts. Verification split: the fresh-round path is proven live with the stub (toast, gating indicator while the round runs, auto-pass to Ready); the `review` arm is graded by reading, since no no-burn path reaches phase `review`. Richer surfaces stay with 004-07.
4. **Typed not-running errors** (`services/board.ts:20-28`), defensive typing only: both getters throw `new ApiError("SERVICE_UNAVAILABLE", { status: 503, message: "board service is not running" })`. api.md registry row meaning: an RPC reached a stopped board service (shutdown; boot order forbids a start race); no `data`. The seven non-route importers are deliberately left as-is: they run only inside work the service itself starts, and if the throw ever fires there the `ApiError` degrades exactly like today's bare `Error`, just typed.
